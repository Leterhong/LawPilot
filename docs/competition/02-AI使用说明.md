# 第一部分：产品内的 AI

## 1. AI 在系统中承担的三个角色

### 角色一：事实抽取与追问决策

**输入**：用户的自由陈述（"老板欠我三个月工资，没签合同，有微信聊天记录"）
**任务**：判定案由 → 从陈述中抽取已满足的事实项 → 判断还缺什么 → 决定下一个问题
**输出**：结构化事实 + 下一个问题 + 自然语言回复

涉及代码：`backend/app/services/agent/engine.py`、`prompts.py`

设计要点：**LLM 不可用时不阻塞流程**。每一轮先尝试模型决策，失败或未配置密钥时回退到 `knowledge_base.py` 的确定性追问脚本。这意味着 Demo 环境没有密钥也能完整走完流程，只是追问措辞不如模型自然。

### 角色二：个案化法律分析（核心）

**输入**：用户逐条陈述的事实 + RAG 检索到的法条
**任务**：生成针对本案的结论、权益分析、对方责任、风险与取证建议
**输出**：5 个字段的 JSON

涉及代码：`backend/app/services/agent/llm_report.py`

这一环是 v1.1 升级的重点。升级前，报告的正文是 8 类案由的硬编码字典，与用户具体陈述无关；升级后，同样的"房屋租赁纠纷"，会因为用户说的押金金额、是否有书面合同、争议类型不同，得到不同的分析。

### 角色三：法律文书生成

**输入**：案由 + 事实 + 当事人信息
**任务**：生成催告函 / 投诉书 / 民事起诉状草稿
**输出**：结构化文书，用户可下载后自行修改

涉及代码：`backend/app/api/v1/documents.py`、`backend/app/contract/report.py`

## 2. 防幻觉机制（这是本产品可被信任的前提）

法律场景下，模型编造一条不存在的法条可能直接导致用户损失。因此系统设计了三道闸门，**任一道不通过即整份分析作废并回退模板**。

### 闸门一：事实封闭

- Prompt 中明确：「只能使用「案情事实」中出现的信息，不得臆测或补充任何未提及的细节」
- 事实来源限定为 `workflow.collected_fields`，即用户对追问脚本的逐条回答
- 模型无法访问案件之外的信息

### 闸门二：法条封闭

- 只能引用传入的 citation 列表，编号为 `【法条1】` 至 `【法条N】`
- 系统用正则提取所有引用编号，逐个校验是否在 `[1, N]` 范围内
- **出现任何越界编号，整份分析作废**，回退到模板

代码位置：`llm_report.py::validate_sections`

### 闸门三：结构可校验

- 强制 JSON 输出，五个字段缺一不可，空字符串视为缺失
- 单字段超过 600 字自动截断，避免前端排版崩坏
- JSON 解析失败（含模型输出 Markdown 代码块、道歉语等）→ 回退

### 回退行为

回退不是"报错"，而是"降级"：

| 场景 | 系统行为 | 用户感知 |
| --- | --- | --- |
| 未配置密钥 | 用规则模板 + RAG 法条生成完整报告 | 报告正常，顶部标注「规则模板生成」 |
| 模型超时 / 报错 | 同上 | 同上 |
| 模型输出不合规 | 同上 | 同上 |
| 一切正常 | 个性化分析 | 顶部标注「AI 个性化分析」，并列出实际引用了第几条法条 |

**关键承诺：任何情况下报告都不会是空白或报错。**

### 验证证据

`backend/tests/test_llm_report.py` 用 13 个用例固定了上述行为，包括：

- 引用 `【法条4】` 但只传入 3 条法条 → 断言整份作废
- 引用 `【法条99】` / `【法条0】` → 断言整份作废
- KB 为空时引用任何法条 → 断言整份作废
- 模型返回"抱歉我无法回答" → 断言回退
- 模型抛 TimeoutError → 断言回退且不抛出异常
- 模型返回带 ` ```json ` 包裹的正常内容 → 断言被容忍并采纳

## 3. 检索增强（RAG）如何工作

```
用户查询
   ├─→ [向量检索] query 向量化 → pgvector 余弦相似度 → Top 20
   ├─→ [关键词检索] ILIKE 模糊匹配 title/content/article → Top 20
   │
   └─→ [RRF 融合] score = Σ 1/(60 + rank_i)
          │
          └─→ [Rerank 精排] 可选，远程 rerank 服务或词法降级
                 │
                 └─→ Top 8 → 送入报告「涉及法律」章节
```

**为什么用 RRF 而不是加权求和**：向量相似度与关键词命中分的量纲完全不同，直接加权需要调参且不稳定。RRF 只用排名不用分值，天然免调参，是工业界混合检索的主流做法。

**降级路径**：Embedding 服务不可用时，`_vector_search_*` 抛错被捕获，自动退化为纯关键词检索，响应中标记 `used_hybrid=False`。功能不中断，只是召回质量下降。

代码位置：`backend/app/services/rag/retriever.py`，融合逻辑有 7 项单测覆盖（`tests/test_rag_and_knowledge.py`）。

## 4. 模型治理

系统内置 AI 能力中心（`/settings/ai-center`）与 AI Playground（`/settings/playground`）：

| 能力 | 说明 |
| --- | --- |
| 多供应商管理 | OpenAI 兼容接口，可接入多家，API Key 用 Fernet 加密存储 |
| 模型路由 | 按 feature（如 `agent_report`、`embedding`）指定模型，支持故障转移 |
| Prompt 版本管理 | 提示词可在线编辑、版本回滚，不必改代码重新部署 |
| Token 与成本统计 | 按模型、feature、用户维度统计调用量与花费 |
| 健康检测 | 定期探测各模型可用性 |
| 评测中心 | 在 Playground 中构造测试集，批量跑模型对比 |

**这是本产品的一个差异化设计**：法律 AI 的输出质量高度依赖模型与提示词，把这些当作可运营的资产而非硬编码配置，是它能长期迭代而不失控的原因。

# 第二部分：开发过程中的 AI 使用

OPC 的主题是"一个人 + AI = 一支团队"。本项目的实际分工如下。

## 1. 分工边界

| 环节 | 人 | AI |
| --- | --- | --- |
| 问题定义与用户画像 | ● 主导 | 辅助访谈提纲 |
| 产品架构与模块划分 | ● 主导 | 方案比选、利弊分析 |
| 数据库设计 | ● 决策 | 生成 DDL、迁移脚本 |
| 后端业务代码 | ● 验收 | ● 主力编写 |
| 前端页面 | ● 验收 | ● 主力编写 |
| 单元测试 | ● 定范围 | ● 主力编写 |
| 代码审查 | ● 决策 | ● 静态扫描、缺陷定位 |
| 文档与材料 | ● 定调 | ● 主力撰写 |

一句话：**人负责"做什么"和"对不对"，AI 负责"写出来"和"查一遍"。**

## 2. AI 实际解决的问题样本

以下是可复现的真实案例，说明 AI 在关键节点上的作用：

### 案例 A：静态扫描定位运行时崩溃

用 `ruff check` 扫描全仓库，发现 6 处 `F821 undefined-name`。逐个人工核对后确认其中 2 处是真实缺陷：

- `playground/router.py` 的路由函数 `create_prompt` 与导入的服务函数同名，函数体内调用自身 → 无限递归
- `EvaluationTask` / `EvaluationResult` 未导入 → 调用即 NameError

**价值**：这两个接口在功能清单里"已完成"，人工测试很容易漏掉（谁会去点"Prompt 收藏"和"评测列表"），但评委会。AI 扫描 + 人工判断的组合，把这类问题在提交前清掉了。

### 案例 B：识别"能跑但没意义"的设计

通读 `report.py` 后确认：11 章节中有 4 章是硬编码字典。这不是 bug，代码完全正确，但产品意义为零——用户说了什么都没用。

**价值**：这类问题测试测不出来、报错报不出来，只能靠通读理解意图。AI 在通读 + 对比"产品宣称"与"代码实现"时，比人快得多。

### 案例 C：构建验证与回归保护

- `next build` 全量构建，23 条路由全部通过，首屏 JS 87.5 kB
- 建立 99 项测试，把修复过的 3 个缺陷写成回归用例，防止后续重蹈

**价值**：把"我修好了"变成"我修好了且不会再坏"。

## 3. AI 使用的边界与人工把关点

**AI 不参与决策的部分**：

- 产品定位（"工作流平台"而非"法律问答"）是人定的，AI 曾建议做"法律版 ChatGPT"，被否决
- 8 类案由的选择依据是人调研的
- 免责声明措辞经人工核定
- 所有对外发布的文案由人定稿

**人工强制复核的部分**：

- 涉及法律的任何表述（法条内容、权利主张、赔偿计算）
- 安全相关代码（JWT、密码哈希、字段加密）
- 数据库迁移（不可逆操作）
- AI 生成的测试断言（防止写成"测试通过但什么都没测"）

**已知的 AI 局限**：

- AI 生成的法条内容不可直接采信，本项目的法条数据来自人工整理的种子文件，非模型生成
- AI 倾向于"补全"而非"承认不知道"，因此法律分析必须走封闭约束而非开放式问答
- AI 写的测试容易贴合实现而非需求，需人工审视断言是否真的在验证需求
